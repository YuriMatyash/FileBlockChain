# PrintChain Demo Flow

This is the ordered final review demo. It keeps the project local and clearly separates real smart-contract behavior from mock/demo IPFS and x402 behavior.

## Command order

Run the project in this order:

1. `npm install`
2. `npm install --prefix frontend`
3. `npm install --prefix backend`
4. `npx hardhat node`
5. `npm run deploy:local`
6. `npm run seed:local`
7. `npm run backend`
8. `npm run frontend`
9. Connect MetaMask to `localhost` chain `31337`.
10. Run marketplace and x402 demos.

Use separate terminals for the long-running Hardhat node, backend, and frontend.

## Demo accounts

Use local Hardhat accounts printed by `npx hardhat node`:

| Role | Account |
| --- | --- |
| Deployer / PRINT owner | Account #0 |
| Creator / initial seller | Account #1 |
| Buyer | Account #2 |
| Resale buyer | Account #3 |

Only import local Hardhat test keys. Never use these accounts for real funds.

## Part A — Marketplace x402 access gate

1. Open the frontend, usually `http://127.0.0.1:5173`.
2. Connect MetaMask on Hardhat chain `31337`.
3. Show the large **Marketplace Access Required** card and its `HTTP 402 Payment Required` status. The full marketplace is hidden until access is granted.
4. Explain this is a local x402-style frontend/API gate, not an on-chain restriction on public contract data and not a replacement for an NFT purchase.
5. Confirm it displays the connected wallet, local receiver, and required `1 ETH` amount.
6. Click **Pay 1 ETH and Unlock Marketplace** and confirm the exact `1 ETH` local Hardhat transfer in MetaMask.
7. Explain that the backend verifies the hash on local RPC (sender, receiver, successful receipt, and value) and holds the unlocked wallet only in memory; restarting the backend resets access.
8. Confirm listings become visible. Switch to another Hardhat wallet and confirm it receives `402` and must unlock separately.
9. Confirm the app loads the local `contracts.json` generated by deployment and show the seeded marketplace listing.
10. Point out that the card represents a manufacturing/use license NFT, not merely ownership of a raw STL file. Show the connected wallet's PRINT balance/token information; buyers receive exactly 1 PRINT after a successful NFT purchase, while the purchase itself still uses ETH.

## Part B — Mint/upload flow with mock IPFS

1. Switch MetaMask to the creator account.
2. Open the upload/mint section.
3. Choose a sample manufacturing file such as an STL, STEP, 3MF, CNC file, ZIP, PDF, or technical drawing.
4. Optionally provide a preview image/render.
5. Enter title, summary, category, file type, documentation, and compatibility.
6. Submit the form. The local mock/demo upload adapter automatically creates CID-like values when a backend IPFS upload endpoint is not configured.
7. Explain that default upload mode is mock/demo: the app creates CID-like values locally and stores lightweight metadata in browser session storage.
8. Confirm the mint transaction in MetaMask.
9. Show that the license stores file CID, metadata CID/token URI, creator, mint timestamp, and initial history entry.

## Part C — List and cancel

1. Stay on the owner/creator account.
2. Open **My Owned Licenses**.
3. Enter the actual ETH sale price and list the license.
4. Show the active marketplace listing.
5. Optionally cancel the listing to demonstrate delisting.
6. Re-list the license before continuing to the purchase demo.

## Part D — First purchase with ETH

1. Switch MetaMask to buyer account #2.
2. Refresh/load marketplace data.
3. Buy the listed license NFT with the exact ETH price.
4. Confirm the transaction in MetaMask.
5. Show that ownership changed to the buyer.
6. Switch back to the creator account and show the NFT is no longer under **My Owned Licenses** because the creator no longer owns it.
7. Show that the same NFT now appears in **Created & Sold Licenses** as a compact collapsible row with current owner, listing status, last sale price, and a details/history button.
8. Expand the row to explain that the creator can still track circulation, resale history, and royalty-relevant events without owner-only list/cancel controls.
9. Show the ownership history entry with action `SALE`, price, timestamp, previous owner, and new owner.
10. Explain payment split:
   - 10% royalty is calculated for the original creator/designer.
   - 90% is paid to the current seller.
   - If the first seller is also the creator, both payments go to the same creator address, so the creator effectively receives the full sale price.
11. Confirm the buyer's PRINT balance increased by exactly `1 PRINT`. This reward is minted by the marketplace only after a successful ETH purchase.

## Part E — Resale and royalty demonstration

1. Stay on buyer account #2 after it owns the NFT.
2. List the purchased license for resale.
3. Switch MetaMask to resale buyer account #3.
4. Buy the resale listing.
5. Show ownership changed to account #3.
6. Show history now includes another `SALE` entry.
7. Explain that the original creator still receives the 10% royalty on resale, while the reseller receives 90%.
8. Confirm the resale buyer also received exactly `1 PRINT`; each successful purchase receives one buyer reward.

## Part F — Creator tracking after sale

When returning to the creator account after a purchase or resale:

- **My Owned Licenses** should include only NFTs currently owned by the connected wallet.
- **Created & Sold Licenses** should include NFTs originally created by that wallet but now owned by another wallet.
- Sold-created rows are collapsible and tracking-only; they show token ID, title, current owner, listing status, last sale price, preview/placeholder, seller if listed, current listing price if listed, file type/category, and a short sale/price summary.
- Use the row button to open full details/history.

## Part G — Details, history, and timestamps

On the NFT details view, show:

- Token ID.
- Title and description.
- Creator/designer address.
- Current owner.
- File CID.
- Metadata CID/token URI.
- Mint timestamp.
- Ownership history.
- Price values stored with history entries.
- Current listing status.

## Part H — x402 / HTTP 402 paid-preview demo

The paid-preview route remains intentionally mocked. It demonstrates HTTP `402 Payment Required` behavior but does not perform real x402 settlement. It is separate from the marketplace access payment.

### Browser/UI demo

1. Open a license details view.
2. Click the unpaid preview/demo button if available.
3. Show the HTTP 402-style response/error.
4. Click the mock-paid/demo authorization button.
5. Show protected preview JSON/data.

### Terminal demo

Unpaid request, expected HTTP `402`:

```bash
curl -i http://127.0.0.1:4000/api/paid-preview/1
```

Mock-paid request, expected HTTP `200`:

```bash
curl -i -H "x-printchain-demo-payment: paid" http://127.0.0.1:4000/api/paid-preview/1
```

### Marketplace API checks

Before unlock (expect `402`):

```bash
curl -i http://127.0.0.1:4000/api/marketplace-access/0x3C44CdDdB6a900fa2b585dd299e03d12FA4293BC
```

After the frontend verifies a valid `1 ETH` transfer for that wallet, repeat the command (expect `200`). An invalid hash returns `400`; a verified transfer under `1 ETH` returns `402`. A second wallet must unlock separately.

## What to say during review

- PrintChain is a DApp marketplace for digital manufacturing license NFTs.
- Each NFT represents a license to use, print, or manufacture the digital model/file.
- PRINT is a reward token, not the purchase currency.
- Marketplace purchases use local test ETH.
- The marketplace enforces 10% creator/designer royalty on sales.
- Ownership history, price values, and timestamps are kept on-chain.
- Files are not stored on-chain.
- IPFS upload is mock/demo by default, with CID-like metadata for local review.
- x402 has two local demos: a frontend/API marketplace gate that verifies a local 1 ETH transaction and an independent mock-paid preview route. The gate resets when the backend restarts and does not make public contract data private.
